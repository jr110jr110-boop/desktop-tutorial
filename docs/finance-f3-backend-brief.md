Context: F1 (ledger, treasury, receivables, VAT) and F2 (assets, payroll, Sepidar outbox) are green. The company wants the finance package to cover everything a developed technology/manufacturing company needs, at the level of Sepidar / Hamkaran System. This brief closes the remaining gaps. Everything in /home/claude/innco/docs/finance-backend-brief.md (ground rules, no invented statutory values, ★ = provisional, segregation of duties, one posting path via AccountingEvent → voucher) and quality-backend-brief.md ("CI loop", "Addendum") stays binding. Study the F1/F2 code first (src/Services/NasbNiro/Finance/*, LedgerEntities.cs, FinanceSeed.cs, the finance smoke section). ## 0. Amendments by the company (2026-10-21, binding — override anything below that conflicts)
- **Persian (Shamsi) calendar only, for now.** All dates shown, entered, exported and printed are Persian; fiscal years/periods are Persian. Do NOT expose a Gregorian option anywhere (no API field, no setting, no UI value, no export column) and do not build Gregorian fiscal years, even for the second legal entity (section 2: build the entity seam with Persian calendar only; drop the `calendar kind` Gregorian value from the brief). Internally keep all date logic behind one small abstraction (`IFiscalCalendar` with the Persian implementation) so that a Gregorian implementation can be added later by one class + a setting, without touching reports or services. Storage stays `DateTime`. Document in a short note (`docs/calendar-seam.md` in the repo) exactly where to add it.
- **Goal: the books must be acceptable to the tax office, the social insurance organisation and external auditors.** So build for statutory acceptability: legal books (دفتر روزنامه و دفتر کل) in the standard Iranian layout and numbering, gapless final voucher numbers, no deletion of final records, immutable audit trail, period lock, printable standard statements, VAT/transaction-list data in the layouts those offices use. Where the exact official layout is unknown, make the columns configurable data and say so in the report.
- **Fallback: connect to Sepidar if the offices do not accept PMIS books.** Therefore add (section 1b): a full **voucher export for Sepidar** (all final vouchers of a period as an Excel/CSV in a configurable column layout: voucher no, date, description, account code (mapped through `FnAccount.SepidarCode`), detail code (`FnDetailAccount` Sepidar mapping), debit, credit, cost centre, project), with a mapping screen for account/detail codes, per-period export records (hash, who, when) and re-export guard, so that finance can load PMIS vouchers into Sepidar at any time. The `ISepidarClient` interface stays; the real API client is added when documentation arrives. The F2 outbox (tax/insurance data) remains the default path; the full-voucher export is a switch (`Finance:SepidarFullExport` off by default).

## 1. Migration from Sepidar and parallel run (highest priority — go-live depends on it)
- Import wizard endpoints (FINANCEMANAGER): (a) chart of accounts from Sepidar export (Excel: code, title, level, nature) with mapping of unknown codes to the PMIS chart or creation; (b) detail accounts (تفصیلی) with type guess and manual correction list; (c) opening balances per account and detail (extends the existing opening import: dry-run mode that returns the full validation report before anything is saved, then commit); (d) optional historical vouchers import (Excel: date, number, description, account, detail, debit, credit) into a flagged `Imported` year — read-only, never mixed with PMIS-made vouchers, excluded from segregation checks.
- **Parallel-run comparison**: upload Sepidar's trial balance (Excel) for a period; the system compares account by account and detail by detail against the PMIS ledger and returns a difference report (matched / PMIS only / Sepidar only / amount differs) and a sign-off record (FINANCEMANAGER) per period. Go-live criterion ★: three consecutive months with zero unexplained differences.

## 2. Legal-entity seam (the company is moving to Germany)
- `FnLegalEntity` (code, name, jurisdiction IR/DE, base currency, fiscal calendar kind {Persian, Gregorian}, isActive). `FnFiscalYear` gets `LegalEntityId` (existing rows → entity 1). Vouchers, periods, bank/cash accounts, customers' invoices, assets, payroll runs resolve their entity through their fiscal year or bank account; reports and all endpoints take an optional `legalEntityId` (default: the user's default entity, a user setting).
- Gregorian-calendar fiscal years for DE entities (1 Jan–31 Dec ★ editable, periods by calendar month). Chart of accounts: `FnAccount.Jurisdiction` already exists; a DE chart is NOT seeded (accountant defines SKR03/SKR04 later) — only the structure works.
- Intercompany: `FnIntercompanyPair` mapping two entities' accounts; an intercompany posting creates mirrored events in both entities; elimination report (consolidation view: sum of entities by account with eliminations, currency translation by rate table — rates are inputs).
- Do NOT build German statutory rules now (VAT, payroll, GoBD export). Keep the seams.

## 3. Foreign currency (استاندارد اثرات تغییر نرخ ارز — verify the standard number against the licensed text)
- `FnCurrency` (code, title, decimals, isBase), `FnExchangeRate` (currency, date, buy, sell, average, source {Manual, Central bank, Market}, rate type {Official, Negotiated, Free ★}) — rates are inputs, never seeded.
- Voucher lines already carry currency amount and rate: add enforcement — a line with currency needs a rate row for its date or an explicit rate; document rate on supplier invoices / sales invoices / payments.
- Monetary-item revaluation at period end (`POST gl/fx-revaluation`): for accounts flagged `IsMonetaryForeign` (cash/bank in currency, receivables, payables, advances in currency, loans) recompute base-currency balance at the closing rate per detail; the difference posts to 60303/80302 (FX gain/loss) in an Auto voucher dated period end, with an automatic reversal on day 1 of the next period (config ★ on/off). Realised differences on settlement (invoice rate vs payment rate) post automatically at payment.
- Letters of credit and foreign purchase: `FnLetterOfCredit` (supplier, bank, currency amount, opening date, expiry, margin/deposit %, fees, status {Opened, Documents received, Paid, Expired, Cancelled}) with postings: margin deposit (10501-type deposit account), fees, settlement and link to the purchase order and the foreign supplier invoice. Currency exposure report (open foreign receivables/payables/LC by currency).

## 4. Budgeting and commitment control
- `FnBudget` (legal entity, fiscal year, version, kind {Annual, Revision}, status {Draft, Approved, Superseded}), `FnBudgetLine` (account (any level) or cost centre or project/contract, period 1..12, amount). Import/export Excel. Approval FINANCEMANAGER + CEO (two people).
- Budget vs actual reports (month, YTD, full year; by account, cost centre, project) with variance and %; forecast = actual YTD + remaining budget ★ or run-rate (selectable).
- Commitment check: purchase requests/orders and payment requests compute remaining budget for their cost centre/project/account; mode per budget {Off, Warn, Block with CEO override ★ default Warn}. Add the check call into the existing procurement approval gates (read-only helper, the gate decision stays with the human; a blocked item shows the reason).
- Capital budget lines linked to asset acquisitions.

## 5. Costing completeness (industrial accounting)
- **Job costing close-out**: when a work order is Done and shipped, `POST costing/workorders/{id}/close` computes final cost (material, labour, overhead absorbed, subcontract), compares to WIP balance, posts the transfer WIP → finished goods/COGS (per delivery: COGS recognised on `CustomerDelivery` of serial units at the work order's per-unit cost) and the residual variance to a variance account (70107/new 70109 "انحراف بهای تمام‌شده" ★). Reopening only by FINANCEMANAGER with reason (creates reversal).
- **Overhead absorption and allocation**: `FnOverheadRate` (cost centre or work centre, base {LabourHours, MachineHours, DirectLabourCost, DirectMaterialCost}, rate per base, valid from/to — inputs). Period-end allocation `POST costing/allocate/{periodId}`: indirect cost centres' actual costs (from vouchers 702xx by cost centre) allocated to producing cost centres by step-down (allocation key table `FnAllocationKey`: percentages or statistical bases such as area, headcount, kWh — inputs) then absorbed into work orders by the overhead rates; under/over-absorbed overhead reported and posted to a variance account at period end.
- WIP report per work order (material issued, labour, overhead, subcontract, less transferred), cost sheet (برگه بهای تمام‌شده) per work order and per serial unit, planned (estimate) vs actual.
- Standard costs optional: `FnStandardCost` per item; purchase-price and usage variances reported (purchase price variance already exists).
- **Revenue recognition for construction contracts** (percentage of completion): per contract setting `RevenueMethod {OnInvoice (default), PercentOfCompletion}`; when PoC: progress from project control (cost-to-cost or physical progress setting ★), monthly run `POST receivables/revenue-recognition/{periodId}` posts revenue earned − recognised, unbilled receivable (10701/new 10308 "مطالبات تکمیل‌نشده" ★) or billings in excess (30303 deferred income); expected-loss provision when EAC cost > contract price (from project control EAC). Reversal-safe (cumulative method). Retention and advances unaffected.

## 5b. Prepaid, accruals, provisions

## 6. Financing and guarantees
- `FnLoan` (bank, facility type {Loan, Murabaha, Overdraft, Leasing}, contract no, amount, currency, start, end, rate %, repayment schedule kind {Equal principal, Annuity, Custom}, fees, collateral text, status): generates the instalment schedule (principal/interest split; Persian-calendar due dates), accrual of interest monthly (draft entry, approve), instalment payment from treasury splits principal/interest/penalty. Facility limit and utilisation report. Loan covenants are not built.
- Bank guarantees issued on the company's behalf and received (connect to existing `FnGuarantee` / `PcGuaranteeInfo`): issuance fee amortised over the guarantee period via `FnDeferral`; margin deposit; release/extension events; expiry alerts (existing) and a consolidated guarantee register for finance with exposure by bank.

## 9. Controls, audit trail and housekeeping (what auditors ask for)
- **Audit trail**: `FnAuditLog` (append-only; entity, id, action, before/after JSON of changed fields, user, timestamp, IP) written for: accounts, details, vouchers (all state changes), periods/years, mappings, rates, bank accounts (IBAN changes), employees' bank/IBAN, budget, assets. Queryable by FINANCEMANAGER/CEO/auditor role `AUDITOR` id 28 ("حسابرس", read-only to all finance data incl. audit log, no payroll personal data unless CEO grants per period ★). No deletes anywhere in finance except drafts; deleted drafts are logged.
- Voucher attachments (document ids), required-attachment rule per account/type (data), voucher approval thresholds (data: amounts above X need CEO ★ — inputs, none seeded), recurring/template vouchers `FnVoucherTemplate` (system drafts monthly instances, human checks), voucher copy, mass voucher entry (Excel import into drafts).
- Period-close checklist `FnCloseChecklist` (auto-computed items: unposted events, draft/checked vouchers, bank reconciliations approved, depreciation approved, payroll posted, FX revaluation done, accruals/deferrals run, overhead allocation done, inventory reconciliation clean, VAT season prepared, intercompany matched); lock requires all green or an override with reason.
- Reconciliation tools: supplier statement reconciliation (import supplier statement lines, match to AP), customer confirmation letters data (balance at date), inter-account reconciliation (GRNI vs receipts exists), sub-ledger vs control account checks for all control accounts (receivables, payables, assets, payroll payable, loans).
- Data-protection: salary and personal data masking in logs; export of finance data only for the roles allowed.
